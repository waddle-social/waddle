# Waddle for iPhone, iPad and Mac

One SwiftUI codebase, two targets (`Waddle-iOS`, `Waddle-macOS`), on top of
the same Rust XMPP core the web and Android clients use.

## Architecture

```
Waddle/                      SwiftUI app target
  App/                       AppState (auth → session), navigation, preferences
  Auth/                      device-authorization sign-in, Keychain credential
  Shell/                     iPhone tab shell, iPad/Mac split view, menu commands
  Features/                  Conversation, Navigation, Details, Account, Calls, Community, Events screens
  Design/                    Polar Huddle tokens, theme and shared components
  Resources/                 bundled fonts and their licences
  Platform/                  notifications, APNs registration
  Calls/                     call media over the LiveKit Swift SDK
  Bridge/                    FFIXmppPort: WaddleKit's XmppPort over UniFFI
  RustClient/Generated/      UniFFI bindings (regenerated by the build script)
WaddleTests/                 design-system tests and snapshot goldens
WaddleKit/                   UI-free core (Swift package; depends on swift-crypto)
  Identity/ Model/           typed JIDs and parsed stanzas
  Files/                     XEP-0448 encryption and decryption, XEP-0300 digest checks
  Timeline/                  the conversation reducer
  Calls/                     the 1:1 call slot: XEP-0353 invitations, Jingle sessions
  Stores/                    presence, unread, inbox, typing, delivery, pins, community feed, events, sticker packs…
  Session/                   SessionCoordinator: event routing and actions
  Compose/                   markdown → XEP-0394, mentions → XEP-0372
```

- **XMPP-native.** Chat data travels only over XMPP through the Rust core.
  HTTP is used for device-authorization sign-in, for XEP-0363 upload PUTs
  (a chat attachment is uploaded as XEP-0448 ciphertext; a sticker pack's
  pictures as they are, since anyone sent a sticker fetches its picture),
  for GETs of XEP-0448 ciphertext from its XEP-0447 source, and for GETs of
  a story's picture or video from the http(s) address its author published
  (a story's file is uploaded as it is, since the whole community reads it). Call media
  goes to the SFU that the Jingle transport names; the call itself is set up
  and ended over XMPP.
- **Parse once.** `Bridge/` converts UniFFI records into WaddleKit's typed
  values at the boundary; nothing downstream sees raw strings.
- **WaddleKit has no UI or FFI dependency**, only swift-crypto (CryptoKit
  on Apple platforms, BoringSSL on Linux), so its logic is unit-tested on
  Linux and macOS with `swift test`. It ports the Android client's
  protocol logic: XEP-0359 dedupe, ranked XEP-0444/0308/0424/0425 mutations,
  XEP-0430 inbox reconciliation, XEP-0333/0490 read state.

## Design system

The apps follow Polar Huddle, the design system the web and Android clients
use (`design/src/preset.ts`).

- **Tokens.** `Design/WaddleTokens.swift` is generated; never edit it. After
  changing the preset, run `bun scripts/generate-design-tokens.mjs`. Chat's
  `tokensCheck` task fails when the file is stale.
- **Colours** follow the appearance: Night in dark, Daylight in light. Use
  `Theme.Colors`, not system colours.
- **Type.** Three bundled variable fonts (`Resources/Fonts`), applied with
  `.huddleText(Theme.Typography.body)`. Sizes follow Dynamic Type.
- **Surfaces, motion, controls.** `Surfaces.swift` (`huddleSurface`,
  `HuddleCard`), `Motion.swift` (`huddleAnimation`; under Reduce Motion a
  view swaps movement for a fade) and `Controls.swift` (button, chip, tag, toggle, segmented control).

## Prerequisites

- Xcode 16.3 or later (the LiveKit Swift SDK needs Swift tools 6.1)
- `rustup` (the toolchain is pinned in `server/rust-toolchain.toml`; see
  `docs/rust-toolchain-bump.md`)
- `xcodegen` (`brew install xcodegen`)

## Build

```bash
# 1. Rust core → XCFramework + Swift bindings
bash scripts/build-xcframework.sh --debug

# 2. Xcode project (only needed after adding/removing files)
cd apps/apple && xcodegen generate

# 3. Build
xcodebuild -project apps/apple/Waddle.xcodeproj -scheme Waddle-macOS -destination 'platform=macOS' build
xcodebuild -project apps/apple/Waddle.xcodeproj -scheme Waddle-iOS -destination 'generic/platform=iOS Simulator' build
```

`Waddle.xcodeproj` is generated from `project.yml` and committed. Regenerate
it whenever you add or remove source files.

## Test

```bash
# Core logic
cd apps/apple/WaddleKit && swift test

# Design system, hosted by each app (needs the XCFramework from step 1)
xcodebuild -project apps/apple/Waddle.xcodeproj -scheme Waddle-macOS -destination 'platform=macOS' test
xcodebuild -project apps/apple/Waddle.xcodeproj -scheme Waddle-iOS -destination 'platform=iOS Simulator,name=<an iPhone>' test
```

`WaddleTests` renders every design-system component in Night and Daylight
and compares it with the goldens in `WaddleTests/__Snapshots__`, one set per
platform. After an intended visual change, delete the affected goldens and
run the tests once to record new ones (that run fails), then commit them.
Screen tests (`ShellScreenSnapshotTests`) host a whole screen in a window,
fed by `SampleSession`: a signed-in session over the scripted `FakePort`,
with no network. Whole screens draw system chrome that changes between OS
releases, so they are compared only on the release the goldens were recorded
on and skipped elsewhere (`screenGoldenOSVersion`).

The goldens were recorded on iOS 27 and macOS 27, on a machine with a
day-month-year date format; screens that show dates depend on it. The bundled fonts render
alike on older releases; SF Symbols do not, so a snapshot with detailed
symbols passes a lower `precision`.

## Call media

`Waddle/Calls/LiveKitCallMediaController.swift` joins the SFU room named by the
credentials in the Jingle transport and publishes the microphone and camera.
WaddleKit checks the token's grant and maps the server's XEP-0215 services to
ICE servers before it connects; it never imports the SDK.

`Features/Calls/CallDock.swift` is the one call surface on every platform: a
card above the signed-in shell, from the first ring to the reason the call
ended. It derives what to show from the call slot and the media phase
(`CallStage` in WaddleKit); `CallDockView` draws each stage without a session,
so the snapshot tests cover them all.

Outside the dock a call is heard and seen through the platform. `CallAlert`
in WaddleKit says what the call slot asks for: a ring for a call coming in
(silenced by Do Not Disturb), ringback for a placed call while the other side
is ringing; `CallRingPlan` says how that reaches the person.

On a Mac `Calls/CallRinger.swift` plays the tones, which `CallTone`
synthesises, and posts a notification with Accept and Decline while Waddle is
not in front.

On an iPhone or iPad calls go through CallKit. `SystemCallTracker` in WaddleKit
turns the call slot into what the system's call screen is told, each thing
once; `Calls/SystemCallCenter.swift` tells it and carries Answer, End and Mute
back to the slot. A mute made in the dock is told to the system too, and a
call whose session the other side replaces stays the same system call. The system owns the audio session of a call it manages:
`Calls/SystemCallAudio.swift` starts the media engine when CallKit activates
the session and stops it when CallKit takes it back. A call the system does
not manage (it arrived under Do Not Disturb, or the system refused it) keeps
the media engine's own session handling, and shows in the dock without a ring.
A room's call is reported too, as a call placed to the room. Only ringback is
played by the app.

On iPhone and iPad, PushKit wakes a closed or suspended app and reports the
incoming call to CallKit before restoring the XMPP session (see Push notifications).

A room's call (XEP-0272) shows in the same dock as `GroupCallDockView`, staged
by `GroupCallStage`: the room, the people in it from `GroupCallRoster` (the
SFU's participants while connected, the room's Muji presence otherwise), and
mute, camera, raise-hand and leave controls. A room with a call we are not in
shows `RoomCallBanner` above its timeline, with a Join button.

The SDK version is pinned in `project.yml`. To check a new SDK or SFU version,
run the connect tests against that SFU version locally (they skip without the
URL):

```bash
docker run --rm -p 7880:7880 -p 7881:7881 -p 7882:7882/udp \
  livekit/livekit-server:v1.11.0 --dev --bind 0.0.0.0 --node-ip 127.0.0.1

TEST_RUNNER_WADDLE_LIVEKIT_TEST_URL=ws://127.0.0.1:7880 \
  xcodebuild -project apps/apple/Waddle.xcodeproj -scheme Waddle-macOS \
  -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO \
  -only-testing:WaddleTests-macOS/LiveKitCallMediaTests test
```

The image tag should match `appVersion` in
`infrastructure/waddle.cloud/charts/livekit-sfu/Chart.yaml`.

## Push notifications

The app registers its APNs token with `push.<domain>` (Waddle's XEP-0050
register-device command) and enables XEP-0357 on the account. The Push Service
sends each device a minimal alert: a generic banner chosen by notification
class (the strings live in `Waddle/en.lproj/Localizable.strings`), the unread
badge, and a routing object that opens the right account and conversation when
tapped. It carries the sender and the message only for a conversation where
the account turned on "Show messages in notifications" (its details screen);
the system draws that alert, so the app's own preview setting does not apply
to it.

"Push notifications" in Settings turns push off for the install: it retires
this device's registrations (`PushTokenRegistrar.turnOff`), for alerts and
calls and for every account on it, and stops asking Apple for tokens. The
account's other devices share the push node and keep receiving.

To receive pushes, add the Push Notifications capability to your signing
team's App ID. The server needs `WADDLE_APNS_KEY_PATH`, `WADDLE_APNS_TEAM_ID`,
`WADDLE_APNS_KEY_ID` and `WADDLE_APNS_BUNDLE_ID` (all four, or none to leave
APNs off); debug builds register as `sandbox`, release builds as `prod`.

The server also supports PushKit tokens registered as `platform=apns` with
`app-id=<bundle id>.voip` on a separate node. XEP-0353 invitations use
APNs push type `voip`, priority 10, and that `.voip` topic. Their payload has
only a `waddle` object (no `aps`): `v`, `class=call`, caller bare JID in
`conversation`, stanza `item`, `node`, and `call` containing `sid`, `video`,
Unix-second `expires` (receipt time plus 45 seconds). Only the XMPP stream
proposal supplies the caller's full JID for protocol responses. It carries no
display name or body. Ordinary notifications stay on the alert node.

On iPhone and iPad the app creates its PushKit registry at process launch,
registers the VoIP token beside the alert token, and reports every VoIP push
to CallKit immediately, even before a scene or session exists. It then shares
session restoration with the UI, retries temporary failures (including a
keychain locked before first unlock) until the push deadline, validates the
node's server and account, and waits for the XMPP stream proposal to fill
the normal call slot. Answer waits for that slot and an online connection;
an early decline remembers the finished call without sending anything. When
its stream proposal arrives, the app rejects it once to the proposer's full
JID without ringing; a bare-JID or self-originated proposal gets no response.
Sign-out retires both registrations and turns off VoIP push types. The Mac
keeps its existing alert registration and running-app call notifications.

There is no cancel push: the system screen waits for stream delivery or the
push deadline. The server delivers the proposal and any later retract in
order after the restored session sends presence, so a cancelled call cannot
remain answerable from push metadata. The push deadline ends the system
screen without suppressing a later stream proposal's own ring window. A
pending system answer uses the answer action's deadline instead, and survives
adoption under Do Not Disturb. Once the slot adopts a call, its 60-second
unanswered timer applies instead of the push deadline. Before the session
loads, the caller name is the JID's local part (or domain); there is no contact
cache. APNs environment selection follows `DEBUG`, as for alerts, so signing
and server configuration must match the build.

PushKit delivery requires a device. Before release, check:

- A killed app rings, and answering on the lock screen gives audio.
- A stream-first duplicate push preserves the call; a second call's push
  reports then ends while the first keeps ringing.
- Repeated report-then-end pushes are not throttled or terminated by iOS.
- Answer works when microphone permission has never been granted.
- A TestFlight build receives production VoIP pushes.
- Offline sign-out disables VoIP delivery and retires both registrations
  on the next opportunity.

Call pushes are also emitted when the account has connected or hibernated
sessions, so a client may receive both the XMPP proposal and its VoIP push.
A client already showing the call re-reports a push with the same `call.sid`
(the XEP-0353 call id) under the existing CallKit id, ignoring the duplicate
report's result and keeping a single incoming-call surface. The server's
persisted reason remains `offline_call` for these invitations too.

## Xcode Cloud and TestFlight

Xcode Cloud archives both apps and hands them to TestFlight. The repository
carries everything the build needs; the workflow itself lives in App Store
Connect.

`ci_scripts/ci_post_clone.sh` installs the Rust toolchain pinned in
`server/rust-toolchain.toml` and builds the XCFramework. An archive action
builds only its own platform's device slices (`--platform ios` or
`--platform macos`), since every slice is a separate fat-LTO release build.
Build and test actions build every slice.

Xcode Cloud does not resolve packages itself, so the project carries its own
`Waddle.xcodeproj/project.xcworkspace/xcshareddata/swiftpm/Package.resolved`.
When WaddleKit's dependencies change, update it to the same pins as
`WaddleKit/Package.resolved`. It also pins the test-only snapshot library.

Signing is automatic for team `6KXCJGJ45W`; Xcode Cloud uses cloud-managed
certificates and replaces `CURRENT_PROJECT_VERSION` with its own build number.
The macOS app is sandboxed (App Store requirement) with network access in
both directions (call media receives on the sockets it opens), the
microphone and camera, and read access to files the user picks.

### One-time setup

1. **App ID.** In Certificates, Identifiers & Profiles, enable Push
   Notifications on `p4x.waddle.social`.
2. **App record.** In App Store Connect, the Waddle app (bundle ID
   `p4x.waddle.social`) needs both the iOS and the macOS platform.
3. **Workflow.** In Xcode, *Integrate → Create Workflow…* (the first time
   Xcode Cloud is set up for Waddle) or *Integrate → Manage Workflows…*, and
   create a workflow on the Waddle product:
   - Start condition: *Branch Changes* on `main`. Optionally restrict it to
     *Files and Folders* `apps/apple/`, `scripts/build-xcframework.sh`,
     `server/crates/`, `server/Cargo.lock` and `server/rust-toolchain.toml`,
     so unrelated merges do not spend compute hours.
   - Environment: latest release Xcode (16 or later; the project format
     needs it), *Clean* enabled.
   - Action *Archive – iOS*, scheme `Waddle-iOS`, deployment preparation
     *TestFlight and App Store*.
   - Action *Archive – macOS*, scheme `Waddle-macOS`, deployment preparation
     *TestFlight and App Store*.
   - Each archive must use its own app's scheme. There is deliberately no
     combined scheme: archiving both apps in one action builds the macOS app
     against the iOS-only XCFramework and fails with "no library for this
     platform was found".
   - Post-action *TestFlight Internal Testing* for both archives, with the
     tester group that should receive every build.
4. **Build number.** In App Store Connect, *Xcode Cloud → Settings → Build
   Number*, set the next build number above any build already uploaded.
5. **Export compliance.** Neither target declares
   `ITSAppUsesNonExemptEncryption`, so each build waits in *Missing
   Compliance* until someone answers the encryption questions for it in App
   Store Connect. The app ships its own encryption, not only the OS's: TLS
   through rustls/ring in the Rust core, and XEP-0448 AES-GCM through
   swift-crypto. Once the classification is settled, declare it in
   `project.yml`. `INFOPLIST_KEY_ITSAppUsesNonExemptEncryption: NO` sends
   builds straight to testers; `YES` also needs
   `INFOPLIST_KEY_ITSEncryptionExportComplianceCode` from App Store Connect.

`Waddle/PrivacyInfo.xcprivacy` declares the app's required-reason API use
(`UserDefaults`, reason CA92.1). Update it when the app starts using another
API on Apple's required-reason list.
