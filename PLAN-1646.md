# Plan: #1646 — durable room effect outbox with per-lifecycle FIFO (rev 4)

P0.4 slice 3 of 4. Typed effect intents commit in the room-mutation transaction and a
strict per-lifecycle FIFO drain replaces direct post-commit broadcast.

Rev 2 incorporated plan-review round 1 (marked ▲). Rev 3 added the
eligibility/arming discipline (`available_at_ms`) plus supersession/pre-send
revalidation barriers (marked ●). Rev 4 addresses round 3's five HIGHs
(marked ◆): origin-only arming, superseded-row reaping, unmanaged members-only
producer, attempt-bound terminal effects, and initiator-stream inline frames.

**S2 — Table + key.** `clustering_muc_room_effects`, created inside the existing
`PostgresMucRoomStore::ensure_schema` bootstrap (advisory key `…994` tx,
catalog-probed ALTERs, never the migration ledger):

- `lifecycle_id TEXT NOT NULL`, `revision BIGINT NOT NULL CHECK (revision >= 1)`,
  `ordinal BIGINT NOT NULL CHECK (ordinal >= 0)`,
  `PRIMARY KEY (lifecycle_id, revision, ordinal)`.
- `room_jid TEXT NOT NULL CHECK (room_jid <> '')`.
- `kind TEXT NOT NULL CHECK (kind <> '')` — closed vocabulary in Rust decode only.
- `terminal BOOLEAN NOT NULL`.
- `payload_json TEXT NOT NULL` — serde of a server-side `PersistedRoomEffect`
  mirror (▲ per Q5; all fields typed — JIDs/nicks/status codes, no stringly
  fields).
- ● `available_at_ms BIGINT NOT NULL` — the eligibility stage (destroy-completion
  precedent): `i64::MAX` = staged/inert (not janitor-claimable), a concrete time
  = armed. `superseded BOOLEAN NOT NULL DEFAULT FALSE` (see supersession below).
  `origin_instance_id TEXT NOT NULL` for orphan reconciliation.
- `lease_token TEXT NULL`, `leased_at_ms BIGINT NULL`, `attempt_count BIGINT NOT
  NULL DEFAULT 0`, `last_error TEXT NULL`, `created_at_ms BIGINT NOT NULL`.
- Index `clustering_muc_room_effects_due_idx (available_at_ms, lifecycle_id)`.

Completion DELETEs the row. No done/failed retention.

● **Eligibility model (round-2 findings 1/2/4/5):**
- Rows INSERT in the mutation tx with a producer-chosen stage:
  - **Handler-window** (admin kick/ban/voice effects): `available_at_ms = now +
    HANDLER_GRACE` (default 30s, env-tunable). The producing handler claims its
    exact rows early (exact-PK claim ignores `available_at_ms` but honors lease +
    FIFO head), drains them interleaved with the IQ result per the XEP policy;
    the janitor cannot touch them until the grace elapses, so it can never send a
    ban/voice/config broadcast before the handler's IQ result (finding 1). If the
    handler dies, effects go out late via the janitor — an IQ result that was
    never sent has no ordering to violate.
  - **Arm-on-success** (config-class effects whose outer unit can still roll
    back — owner config, admin-channel config, group-DM config; finding 4): rows
    INSERT inert (`i64::MAX`). The handler arms them (single lease-style UPDATE)
    only after the outer unit (catalog/bookmark work) succeeds, then
    inline-drains; the rollback path DELETEs the staged rows inside its rollback
    mutation's transaction. ◆ **The arm IS the durable success decision, and only
    the ORIGIN instance may make it** (`origin_instance_id` must match — a peer
    janitor can never arm a config row while its producer is still mid-flight,
    and revision comparison is not used as a success proof). Inert config rows
    whose origin never arms them (producer crash between commit and arm) are
    DELETED by the janitor after a TTL — the broadcast is lost exactly as today's
    fire-and-forget loses it on the same crash; config-class staging is a
    reservation, not yet a committed effect.
  - **Terminal** (destroy notification; finding 5): rows INSERT inert. The
    destroy-completion executor (`clustering_muc_destroy_outbox` lease holder)
    arms the terminal effect row only AFTER the app-level durable wipe succeeds,
    preserving today's wipe-first/notify-second order. The destroy IQ path then
    inline-drains the armed terminal row before sending the §10.9 result.
    ◆ **Attempt-bound only (round-3 finding 4):** terminal effect rows are
    enqueued ONLY for `Destroy{completion_attempt: Some(..)}` /
    `DestroyAndReleaseClaim{Some(..)}` commits — i.e. exactly where a
    completion executor exists to arm them and pre-seal recipients exist to
    notify. Attempt-less destroys (admin-API `DestroyRoom`
    `channels.rs:3676` → registry `completion_attempt: None`,
    `destroy_durable_room_without_local_entry`, inactive-room reaping) send no
    completion-based notification today and enqueue NO terminal rows (no
    marker rows). Lane B audits every destroy call site against its actual
    present-day notification behavior; any site that notifies via another
    mechanism keeps that mechanism unchanged.
- ● **Supersession barrier (finding 2):** the destroy tx DELETEs unleased
  non-terminal rows and sets `superseded = TRUE` on currently-leased ones.
  Every worker revalidates immediately before sending: `SELECT … WHERE pk AND
  lease_token = mine AND NOT superseded`; a superseded worker aborts and deletes
  its row. The terminal row's claim CAS additionally requires that no other row
  for the lifecycle holds a live (unexpired) lease, so the destroy presence
  strictly follows any in-flight non-terminal send (bounded by the lease
  timeout). ◆ **Superseded-row reaper:** a janitor step DELETEs superseded rows
  whose lease has expired (the claiming worker crashed before its pre-send
  delete); expired leases do not count as live for the terminal claim — a
  crash-after-claim can therefore never block the terminal notification,
  tombstone GC, or the recreation fence (dedicated test).

**S3 — Effect algebra.** Closed enum `RoomEffect` in
`waddle-xmpp/src/muc/durable/effects.rs`, carried as `RoomEffectIntent<RoomEffect>`:

```rust
pub enum RoomEffect {
    ConfigChanged { status_codes: Vec<MucConfigStatusCode>,
                    recipients: Vec<FullJid> },        // ▲ mutation-time audience
    AdminSelfNotify { frames: Vec<OccupantPresenceUpdate> },   // affected occupants
    AdminRemainingBroadcast { presence_updates: ..., voice_changes: ...,
                              recipients: Vec<FullJid> },
    DestroyNotification { reason, alternate_venue, password,
                          recipients: Vec<DestroyRecipient> }, // terminal
}
```

▲ `ConfigChanged`/`AdminRemainingBroadcast` capture the mutation-time audience
(typed recipient resources) so delayed drains never notify a reactivated
lifecycle's new occupants (effect semantics, not delivery guarantees).

▲ Admin effects are split into two ordered rows (`AdminSelfNotify` ordinal k,
`AdminRemainingBroadcast` ordinal k+1) so XEP ordering can interleave the IQ
result between them (S5).

▲ **Pairing validation (Q3):** `commit_room_mutation` takes a
`RoomMutationEffects` value constructed only via mutation-specific constructors
(`RoomMutationEffects::none()`, `::config(..)`, `::admin(..)`, `::destroy(..)`),
so `Config` + `DestroyNotification` is unrepresentable at the store boundary.
`RoomDurableMutation` itself is untouched (mutation fingerprint at
`muc_durable.rs:107` stays stable).

**S4 — Enqueue in the mutation transaction.** `MucDurableStore::commit_room_mutation`
(+`_with_authority`) grow the `effects: RoomMutationEffects` parameter (breaking
change, no shims). Inside `commit_room_mutation_once`, after the revision bump:
allocate ordinals `0..n` for `next_revision`, INSERT rows in the same tx. Empty ⇒
zero rows. Insertion is serialized by the lifecycle row `FOR UPDATE` (Q4), so all
ordinals of a revision become visible atomically.

▲ **Destroy supersession (round-1 finding 6, hardened per round-2 finding 2):**
the `Destroy`/`DestroyAndReleaseClaim` transaction DELETEs that lifecycle's
pending unleased non-terminal effect rows and marks leased ones
`superseded = TRUE` before inserting the (inert) terminal row. Those broadcasts
describe a room that no longer exists; supersession keeps the terminal effect at
FIFO head, so ownership-gated non-terminal heads can never strand a lease-only
terminal row. Workers revalidate lease+`NOT superseded` immediately pre-send, and
the terminal claim waits for live leases to clear (S2 eligibility model).

Producers compute effects before commit and pass them through: actor handlers
(`UpdateConfig`, `ApplyAdminItems`, `ApplyAffiliationChange`, managed
members-only), admin-channel API commit sites, registry destroy paths
(`handle_destroy_room_message`, unpublished-preparation destroy,
`destroy_durable_room_without_local_entry`) building `DestroyNotification` from
the pre-seal snapshot recipients.

Non-clustered deployments (durable store = None) keep today's direct-broadcast
path unchanged.

**S5 — Drain.** New module `server/crates/waddle-server/src/room_effect_outbox/`:

- **Claim (per-lifecycle FIFO):** single-statement CAS — conditional UPDATE
  minting a fresh lease token, `WHERE` exact PK AND armed-and-due
  (`available_at_ms <= now`) AND lease absent/expired AND NOT superseded AND
  `NOT EXISTS` earlier `(revision, ordinal)` row for the lifecycle; candidate
  listing is advisory only (Q4: adequate under READ COMMITTED; no advisory lock).
  ● The producing handler's inline claim is an exact-PK variant that ignores
  `available_at_ms` (it authored the rows) but honors lease + FIFO head; terminal
  claims additionally require no live lease on any other row of the lifecycle.
- **Ownership:** non-terminal effects require the current room claim
  (`check_exact_claim_fence`); not-owner ⇒ release with flat delay, no attempt
  counted — the new claimant drains the backlog. Terminal effects are lease-only.
  ▲ Drain validates the effect's lifecycle against the current lifecycle row
  before executing (stale-lifecycle effects for a recreated JID never fire —
  belt to S6's braces).
- **Execution:** rebuild stanzas from typed payload via existing builders.
  ◆ **Initiator-stream ordering (round-3 finding 5):** `connection_registry
  send_to` only queues, so it cannot order effect frames against the handler's
  IQ result on the initiating stream. The inline drain therefore RETURNS the
  initiating session's own frames to the handler, which places them in its
  response frame vector before/after the result exactly as today
  (`muc_admin.rs:1340`, `muc_owner_moderation.rs:404`); the row is completed
  once its frames are handed over/sent. Non-initiator local sessions go via
  `connection_registry`; janitor drains (handler dead, no result pending) use
  `send_to` for everything. ▲ Cross-node via the registered-resource path
  `try_deliver_registered_remote_resource(..., DeliveryKind::DirectFrame)`
  (finding 10 — MucProxy lanes validate room-addressed stanzas and would reject
  generated recipient-addressed frames). No relay wire changes ⇒ no
  `deliver_ordered.vN` bump.
- **Completion:** DELETE under lease token. Failure ⇒ exponential backoff
  (call_teardown constants); attempt-capped dead-letter EXCEPT terminal effects
  and infrastructure-transient errors.
- **Trigger:** producer nudges an inline drain for its lifecycle post-commit
  (same lease helper as the janitor). Janitor (`tokio::spawn` + interval,
  `Weak<WebSocketState>`, env-tunable interval/batch, `record_janitor_sweep`) is
  the backstop.
- ▲ **Per-XEP ordering policy (finding 8)** — the handler, not the drain, owns
  IQ-result placement, per mutation kind:
  - Kick/307 (§8.2): inline-drain `AdminSelfNotify` → IQ result → inline-drain
    `AdminRemainingBroadcast`.
  - Ban/301 (§9.1), membership-loss/321, voice (§8): IQ result → inline-drain
    both rows.
  - Destroy (§10.9): inline-drain the exact terminal effect (attempt-fenced,
    like today's `complete_leased_destroy_completion`) → IQ result.
  - Config (104/170/171): IQ result → inline-drain.
  - ▲ If a broadcast-before-result inline drain fails: retry within the IQ
    budget; on exhaustion do NOT send a success result out of order — the commit
    is durable, the janitor completes the broadcast, and the requester's IQ times
    out (never a false failure reply for committed state: no error reply either,
    matching today's ambiguous-outcome discipline).

**S6 — Destroy contracts (finding 7) + tombstone/dormancy.**
- `clustering_muc_destroy_outbox` REMAINS and still owns durable wipe + SFU +
  claim bookkeeping; its notification send moves to the effect drain.
- ● **Outbox dependency (round-2 finding 5):** the terminal effect row is inert
  until the destroy-completion executor arms it after the durable wipe succeeds
  — wipe-first/notify-second is preserved under both inline and janitor drains.
- ▲ **Recreation fence extended:** `destroy_completion_blocks_create_in_tx`
  gains a second predicate — `Create` is also blocked while a pending
  `terminal = true` effect row exists for the same `room_jid`
  (`recreation_blocked_by_pending_effects`). A new lifecycle at the JID cannot
  commit until the old lifecycle's destroy presence has been sent, so stale
  destroy frames can never interleave with a successor room.
- **Tombstone retention:** ● lifecycle tombstone rows are retained while rows
  for that lifecycle exist in EITHER outbox (`clustering_muc_room_effects` OR
  `clustering_muc_destroy_outbox` — the completion path needs the tombstone for
  recovery and stale-lifecycle fencing, `muc_owner_moderation.rs:306`);
  lifecycle GC gains both anti-join guards + tests.
- **Dormancy:** `Dormancy` writes no rows; dormant lifecycles keep any undrained
  backlog; new claimant activation hands drain ownership over naturally. Test
  proves activation-then-drain by the new claimant.

**S7 — Single behavioral delta:** durable-mutation broadcast effects become rows
committed with the mutation, drained per-lifecycle FIFO at-least-once, instead of
fire-and-forget inline sends.
