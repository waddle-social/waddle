# Plan: #1646 — durable room effect outbox with per-lifecycle FIFO

P0.4 slice 3 of 4. Typed effect intents commit in the room-mutation transaction and a
strict per-lifecycle FIFO drain replaces direct post-commit broadcast.

## Context (current main, post #1692/#1693)

- `commit_room_mutation_once` (`server/crates/waddle-server/src/muc_durable.rs:1111-1700`)
  is the single-transaction durable room commit (#1645). It already arms the
  `clustering_muc_destroy_outbox` row in-transaction (`:1640-1665`).
- `RoomEffectIntent<E>`, `RoomEffectOrdinal`, `RoomRevision`, `RoomLifecycleId` already
  exist in `waddle-xmpp/src/muc/durable/lifecycle.rs` as scaffolding for this slice.
  FIFO order per lifecycle = `(RoomRevision, RoomEffectOrdinal)`.
- Direct post-commit broadcasts today (the surface this slice makes durable):
  1. Admin/affiliation presence (`AdminItemsApplied`) — `muc_admin.rs:1331-1399`.
  2. Config-change messages (status 104/170/171/172/173) — `muc_owner_config.rs:459-483`.
  3. Subject reflection — rides ingress dispatcher (`interpret.rs:740-800`) — see scope.
  4. Destroy §10.9 notifications — `muc_owner_moderation.rs:373-466` via the
     destroy-completion outbox (already durable/leased/ownership-independent).
  5. Mediated-invite delivery — `mediated_invites/*`.
- Pattern to follow: `call_teardown_outbox` module shape (schema/types/store/store_jobs/
  drain/tests; claim-token CAS leases; ownership re-check; janitor backstop) and the
  destroy-completion outbox's "inline execution and janitor share one lease helper" rule.

## Scope decisions

**S1 — Effects covered by the new outbox (produced by durable room mutations):**
- `Config` → config-change groupchat message (status codes incl. 104, 170-173).
- `Subject` → §8.1 subject reflection message.
- `Affiliation` / `AffiliationBatch` / `MembersOnlyEnforcement` → admin presence
  updates, moderation removals, voice changes (today's `AdminItemsApplied`).
- `MediatedInviteGrant` → mediated invite message delivery.
- `Destroy` / `DestroyAndReleaseClaim` → §10.9 destroy notification presence
  (moved out of the destroy-completion snapshot's inline send; see S3).

**Out of scope (unchanged):** occupant join/leave presence fan-out (not a durable
mutation — no revision exists), groupchat message routing (ingress effect intents,
#1653-#1657 spine), MUC-PM, recipient delivery guarantees/receipts/DeliveryKey/
idempotency/inter-node mailboxes (explicitly excluded by the issue), `Create`/
`Publish`/`Activate`/`Dormancy`/`MarkUnpublishedCleanup` (no broadcast effect —
and no marker-only pseudo-events are persisted for them).

**S2 — Table + key.** New table `clustering_muc_room_effects` created inside the
existing `PostgresMucRoomStore::ensure_schema` bootstrap (advisory key
`…994` transaction; catalog-probed like the destroy outbox; NEVER the migration
ledger). Columns:

- `lifecycle_id TEXT NOT NULL`, `revision BIGINT NOT NULL CHECK (revision >= 1)`,
  `ordinal BIGINT NOT NULL CHECK (ordinal >= 0)`, `PRIMARY KEY (lifecycle_id, revision, ordinal)`.
- `room_jid TEXT NOT NULL CHECK (room_jid <> '')` (drain routing; denormalized).
- `kind TEXT NOT NULL CHECK (kind <> '')` — Rust-side closed vocabulary (per the
  V1010 lesson: no enumerated CHECK that churns on new kinds).
- `terminal BOOLEAN NOT NULL` — true for destroy-derived effects; selects the
  lease-only (ownership-independent) drain mode.
- `payload_json TEXT NOT NULL` — serde of the typed `RoomEffect` enum (precedent:
  `PersistedDestroyCompletion`; stanzas are REBUILT at drain time from semantic
  fields, never stored as XML strings).
- Lease/retry: `lease_token TEXT NULL`, `leased_at_ms BIGINT NULL`,
  `attempt_count BIGINT NOT NULL DEFAULT 0`, `next_attempt_at_ms BIGINT NOT NULL`,
  `last_error TEXT NULL`, `created_at_ms BIGINT NOT NULL`.
- Index `clustering_muc_room_effects_due_idx (next_attempt_at_ms, lifecycle_id)`.

Completion DELETEs the row (destroy-completion model), no done/failed retention —
the row's existence IS the pending state; per-lifecycle FIFO makes retention rows
head-of-line blockers.

**S3 — Effect algebra.** New closed enum in `waddle-xmpp/src/muc/durable/effects.rs`:

```rust
pub enum RoomEffect {
    ConfigChanged { status_codes: Vec<MucStatusCode> /* typed */ },
    SubjectChanged { subject: RoomSubjectSnapshot, setter_nick: RoomNick },
    AdminItemsApplied { presence_updates: Vec<OccupantPresenceUpdate>,
                        removed_by_moderation: Vec<OccupantRef>,
                        voice_changes: Vec<VoiceChange> },
    MediatedInvite { invitee: BareJid, inviter: OccupantRef, reason: Option<InviteReason>, password: Option<RoomPassword> },
    DestroyNotification { reason: Option<DestroyReason>, alternate_venue: Option<BareJid>,
                          password: Option<RoomPassword>, recipients: Vec<DestroyRecipient> },
}
```

All leaf types are existing typed values (JIDs as `BareJid`/`FullJid`, nicks, status
codes) — no stringly payloads. `RoomEffectIntent<RoomEffect>` is the envelope.
Serde derives live on a `PersistedRoomEffect` mirror in waddle-server if we keep
serde out of waddle-xmpp domain types (decide by inspection; destroy-completion
precedent uses a Persisted* mirror in waddle-server).

**S4 — Enqueue in the mutation transaction.** `MucDurableStore::commit_room_mutation`
(and `_with_authority`) grow an `effects: Vec<RoomEffect>` parameter (breaking
change; no compat shim — repo rule). Inside `commit_room_mutation_once`, after the
revision bump: allocate ordinals `0..n` for `next_revision`, INSERT one row per
effect in the same transaction. Empty vec ⇒ zero rows (no markers). The commit
return (`RoomMutationCommit`) is unchanged; effect rows are keyed to the exact
committed `(lifecycle, next_revision)`.

Producers (compute effects BEFORE commit, pass them in):
- `RoomActor` handlers: `SetSubject`, `UpdateConfig`, `ApplyAdminItems`,
  `ApplyAffiliationChange`, members-only enforcement, mediated invites — each
  already computes the broadcast payload before/at commit; move that computation
  ahead of `commit_durable` and pass it through.
- Registry destroy (`handle_destroy_room_message`, unpublished-preparation destroy,
  `destroy_durable_room_without_local_entry`): build `DestroyNotification` from the
  pre-seal snapshot recipients and pass into the `Destroy`/`DestroyAndReleaseClaim`
  commit. The destroy-completion outbox (`clustering_muc_destroy_outbox`) REMAINS
  and still owns the durable wipe + SFU unregister + claim bookkeeping; its
  `complete_destroy_snapshot` stops sending notifications inline (that send moves
  to the effect drain). Non-clustered deployments (store = None) keep today's
  direct-broadcast path untouched — the outbox exists only where a durable store
  exists.

**S5 — Drain.** New module `server/crates/waddle-server/src/room_effect_outbox/`
(mod/store/drain split per `call_teardown_outbox`):

- **Claim rule (per-lifecycle FIFO):** a row is claimable iff it is the head —
  minimum `(revision, ordinal)` among that lifecycle's remaining rows — AND
  `next_attempt_at_ms <= now` AND lease absent/expired. Claim = conditional UPDATE
  CAS minting a fresh lease token (`WHERE lifecycle_id=? AND revision=? AND ordinal=?
  AND <due predicate> AND NOT EXISTS (earlier row for same lifecycle)`). Only
  `affected == 1` proceeds. Head-blocking is intentional: a failing effect blocks
  its lifecycle, not the table.
- **Ownership re-check:** non-terminal effects execute only while this node holds
  the room claim (`check_exact_claim_fence` / registry-local room lookup, as
  call_teardown's room-scoped gate); not-owner ⇒ release lease with flat delay,
  no attempt counted — the claim's new owner drains the backlog (restart-safe
  handoff). Terminal (`terminal = true`) effects are lease-only, no ownership
  check (destroy-lease independence).
- **Execution:** rebuild stanzas from the typed effect via the same builders the
  direct paths use today (`build_config_change_message`, destroy notification
  builder, admin presence assembly), fan out to local occupant sessions via
  `connection_registry` and hand cross-node recipients to
  `ordered_relay_delivery_bridge` (existing `OrderedRelayMucProxyKind` lanes; no
  relay wire changes ⇒ no `deliver_ordered.vN` bump). Delivery outcome does not
  gate completion beyond today's semantics (slice claims no recipient delivery).
- **Completion:** DELETE under `lease_token`. Failure ⇒ release with exponential
  backoff (call_teardown constants), attempt-capped dead-letter EXCEPT terminal
  effects and infrastructure-transient errors (never dead-letter a destroy
  notification while it can still execute).
- **Trigger:** post-commit the producer nudges an inline drain for its lifecycle
  (same lease helper as the janitor — destroy-completion rule), so happy-path
  latency ≈ today. A janitor (`spawn` + interval, Weak<WebSocketState>, env-tunable
  interval/batch, `record_janitor_sweep`) is the restart/crash backstop.
- **IQ/frame ordering:** for admin IQs the handler awaits the inline drain of the
  rows it just enqueued before sending the IQ result where §8.2/§9.1 ordering
  requires broadcast-before-result (self-kick frames), preserving today's observable
  order; if the inline drain fails the IQ result still goes out (commit is the
  source of truth; the janitor finishes the broadcast).

**S6 — Tombstone retention + dormancy.**
- Lifecycle tombstone rows (`state = 'tombstoned'`) are retained while any
  `clustering_muc_room_effects` row for that lifecycle exists; any GC/cleanup that
  deletes lifecycle rows gains an anti-join guard. (Verify what GC exists today —
  epoch-bounded GC from #1653; add the guard + test.)
- Dormancy: `Dormancy` produces no effect rows, and dormant lifecycles keep any
  undrained backlog; a new claimant's activation makes it the drain owner
  (ownership re-check naturally hands over). Snapshot retention is already durable
  state — add the test proving a new claimant activates and drains the backlog.

**S7 — Single behavioral delta (PR statement):** room mutation broadcast effects
become durable rows committed with the mutation and are drained in per-lifecycle
FIFO order (at-least-once), instead of fire-and-forget inline sends.

## Lanes (sequential, one worktree; gpt-5.6-terra high per lane; orchestrator
verifies between lanes)

- **Lane A — types + schema + store:** `RoomEffect` algebra + envelope wiring in
  waddle-xmpp; `clustering_muc_room_effects` schema in `ensure_schema`;
  store API (`enqueue_in_tx`, `claim_lifecycle_head`, `renew`, `complete`,
  `release`, `list_due_heads`); typed encode/decode; store-level unit tests

- **Lane B — producer threading:** `commit_room_mutation(+effects)` signature

  `commit_room_mutation_once`), every actor/registry call site computes and passes
  effects, ALL fake stores (`RecordingDurableStore`, `FakeDurableStore`, etc.)
  updated (trait-default trap: fakes must not fail-closed).
- **Lane C — drain + wiring:** drain module, inline nudge + janitor, replace the
  direct broadcast sites (muc_admin, muc_owner_config, destroy snapshot send,
  mediated invites, subject if in scope after B), ordering preservation, telemetry
  counters + janitor sweep metrics.
- **Lane D — dedicated suites (acceptance):** FIFO order across restarts (new
  store over same pool), at-least-once handoff (crash between execute and DELETE
  re-executes), destroy-lease independence from ownership, tombstone retention
  until effects drained, dormancy snapshot + backlog handoff to a new claimant,
  head-of-line blocking, lease-token interlock, ownership-handoff drain.

## Open questions for review

1. Subject reflection currently rides the ingress dispatcher
   (`IngressEffectIntent::RoomSubjectMutation` capture). Moving it into this
   outbox may double-produce with the ingress spine (#1657 will flip capture to
   authoritative). Proposal: keep subject OUT of this slice's outbox (leave the
   dispatcher path), note it as a seam for #1657. Agree?
2. Destroy notifications: move the send from `complete_destroy_snapshot` into the
   effect outbox (S4) vs. leaving the destroy-completion outbox owning them and
   scoping this outbox to non-destroy effects only. The issue's "destroy effect
   rows use DB leases independent of ownership" reads as the former; the latter is
   less churn on 2-day-old machinery. Which?
3. `effects` parameter vs. embedding effects in `RoomDurableMutation` variants.
   Parameter keeps the algebra pure; embedding makes illegal states (Config with
   destroy effects) unrepresentable. Preference?
4. Per-lifecycle FIFO claim via NOT-EXISTS-earlier-row CAS: adequate under
   READ COMMITTED with the lease interlock, or do we need the lifecycle row
   FOR UPDATE / advisory lock per lifecycle at claim time?
5. Serde mirror (`PersistedRoomEffect` in waddle-server) vs serde derives directly
   on the waddle-xmpp `RoomEffect`.
