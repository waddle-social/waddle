# Issue 2047 — candidate plan v2

## Scope and invariants
One Academy account and one client session access Academy and Korora, whose deployment, persistence, secrets and administration are independent. The home authenticates the account and binds its resources; the host alone authorizes its resources. The canonical normalized bare account JID is the durable grant and bootstrap subject; a bound full JID carries session/routing provenance and is used only for explicitly resource-scoped operations. Pilot web first; native clients are later separately gated. No shared cluster identity, passwords, second account, identity portability, cross-domain calls/media/push, or general interoperability claim. S2S is off by default; activation requires separate explicit approval, named window and runbook. PostgreSQL remains sole authority for session lifecycle, claims and contiguous frontiers; do not shortcut distributed-actor roadmap sequencing or extend XEP-0198 into arbitrary-node resume.

## F0: architecture gate
Re-audit active paths at the actual implementation base, since v1 baseline c9be4247 diverged from main db6e5338170d71391b69bc80e57626eb13072365. Agree an ADR for two-server XMPP S2S with C2S WebSocket unchanged: exact domain/service ownership, DNS and TLS/SASL EXTERNAL identity, inbound principal, admission policy, component identities, bidirectional routing and IQ correlation, queue and error semantics, backpressure, resource ceilings, failure and restart, and deployment topology. Resolve the server/AGENTS.md S2S-harness prohibition through a reviewed scope change before adding tests; if rejected, stop. Pin applicable RFCs/XEP versions, assess experimental XEP-0503, XMPP conformance scope, and define per-feature advertisement only after evidence. Specify Korora domain later; verify live DNS/certs before activation.

The ADR must select and prove the canonical grant authority and write/enforcement boundary across production SpiceDB, Postgres/PubSub state, projections and multi-replica actors; no claim of a shared atomic transaction. Specify durable, ordered grant/revoke state and monotonic versions or equivalent, transition and crash recovery, stale projection repair, and a fail-closed enforcement fence with acknowledged revocation linearization point. Ensure every protected read, join, send, history request and fanout/queued work is checked or fenced at the chosen boundary. The proof must address checks racing later effects, concurrency across replicas, stale tasks and restart; define precisely already-in-flight behavior. Unresolved architecture or inability to implement the fence blocks the affected feature, not only release. Provisioning or SpiceDB outage fails closed without blocking unrelated traffic. Preserve existing project claims/fencing rules.

## F1: independent dark foundations
1. Fix authorization identifier encoding before accepting external identities. The current SpiceDB '@'→'|' and '.'→'=' mapping is not injective for valid JIDs. Use collision-free typed encoding for every applicable subject/object ID, with unambiguous version/namespace and length/Unicode handling. Inventory existing records and all writers/readers. In a demonstrably empty greenfield namespace use fresh encoding; otherwise design audited migration/reconciliation from authoritative source, detect ambiguity and fail closed, do not infer identity from ambiguous legacy encoding. Exercise production SpiceDB path. This is its own focused PR.
2. Qualify client identities: room = canonical bare room JID; space = canonical service JID plus opaque node; scope message IDs by conversation and issuing authority. Propagate through selection, caches, histories, drafts, unread, reactions, routes and admin targets; prove collision resistance and compatibility for affected state and contracts. Do not expose cross-community UI yet.
3. Separately fix truthful destination classification for missing-to, local bare/full user and each served component, remote and invalid before local namespace handlers. Preserve current local full-JID forwarding and correct IQ result/error routing. While remote routing is off, return appropriate bounded errors without error loops, fabricated ping replies or silent success; document actual behavioral delta and test regressions. Ship any behavior-changing fix only under its own reviewed scope, not accidentally through a dark foundation.

## F2: authenticated transport and dispatch (depends F0)
Transport and parser foundations may follow F0. Dispatch that reaches grants depends on F1's identity codec; protected application dispatch also depends on F3's approved policy and enforcement fence. Do not enable those paths early.
Build bounded S2S ingress/egress for explicit allowlisted domains and authorized services, initially TLS and verified SASL EXTERNAL with no insecure fallback. Validate service identity and from-domain against authenticated peer, recipient ownership, prevent spoofing and unauthorized relay; parse size/depth and apply connection/queue/rate/deadline limits. Separate typed local session and verified remote principals without local account or credential sharing. Integrate message, presence and IQ get/set/result/error and generated events with shared policy; validate IQ ID, type, responder, recipient, context, payload and expiry, at-most-once completion. Preserve RFC error semantics.
Specify each durable ingress/effect handoff, stable retry/dedup identity, ordering scope, timeouts, bounded retry and crash/unknown outcome. Preserve the existing ingress-effect acceptance contract, including frozen target/child identities, its unknown-outcome retry policy and storage-hint no-store behavior; reconcile any necessary change in its own reviewed slice. Socket writes or queue acceptance do not prove recipient delivery; avoid replay expanding recipient sets. Failure/partition must not stall unrelated local traffic. Keep unenabled and unadvertised.

## F3: host authority and scoped admin (depends F0/F1; F2 for end to end)
Implement approved grant boundary in small PRs. Use canonical normalized bare account JIDs for account grants, with bound full JIDs retained for routing and provenance; remote principals need no local account. Distinguish deployment admin, per-community owner, PubSub subscription/affiliation and room affiliation; ownership of one community grants no other authority. Space subscription does not imply child-room membership; public/private discovery, MUC joins, live sends, MAM, events and admin all enforce consistent host policy. Explicit bare-JID bootstrap scoped to one named community via secure operator provisioning/audit, with recovery and revocation. A deleted/reissued home JID must not silently inherit old grants: enforce durable non-reuse for the controlled domains across all provisioning paths or revisit identity/grant lifecycle before pilot. No claims of automatic remote revocation on home account deletion.
Revoke/repair must cover races with join, MAM and queued/live fanout, stale grants and projections, two replicas, actor restart and concurrent grants. Acknowledge revocation only after the specified fence is active. Fail closed while reconciliation is unresolved; do not promise recall of delivered data.

## F4: web pilot (depends F1–F3)
Correct selected homeserver endpoint use. Add explicit remote community discovery and authenticated service identity, invite/add, subscription, authorized join and per-resource actions over the existing home session. Persist bookmarks using XEP-0402; persist qualified joined-space preferences in suitable private home storage with a narrowly defined extension if needed. Preferences are never authority. Preserve unavailable entries during outage and distinguish denial/deletion. Keep leave/unsubscribe/forget/revoke distinct. Recovery includes fresh-device restore and home vs remote restart, occupant cleanup/rejoin, IQ expiration, history reconciliation and own-message behavior on two devices. No global ordering or exactly-once promise: state MUC/MAM/ID guarantees precisely and report uncertain delivery honestly. Shared native client/FFI and Apple/Android/Linux support require follow-up per-client acceptance, not implied by web.

## F5: test and release gate
After reviewed guidance change, use two native independent server processes, separate databases, secrets and independent production-like SpiceDB authorities; normal WSS login and real S2S, no mocks for the acceptance path. Cert and domain validation must be real to the topology. Verify false domain/cert, spoofing, wrong recipient, forged/replayed IQ, relay abuse, malformed/oversized stanzas, queue exhaustion/partitions; malicious localparts and colliding/Unicode IDs; all grant/revoke races and restart; identical room/space names and overlapping IDs; scoped admin and denied private discovery/MAM; unavailability versus denial; two resources, both directions, self-presence, subscriptions and host-authorized paginated history. Separately restart home with remote alive and remote with home alive. Evidence must demonstrate local progress under remote failure and no phantom success.
Run relevant focused, workspace and XEP suites, formatting, Clippy -D warnings, chat lint/tests/Knip, and per-client checks required by changed files; tests on production SpiceDB must be distinguished from local test backend. Check manifests independently from live DNS/TLS. Record pinned commits/config, redacted protocol/client evidence, passed/failed/unverified; skipped prerequisites do not pass. Advertise only validated features; no broader product readiness or E2EE claim. Every material PR follows branch → draft PR → adversarial review CLEAN at exact head (restart after remediation) → green CI → merge; explicit production activation requires a separately approved named window/runbook.

This is a plan approval only. No code, tests, deployment or activation have been completed in this review.
